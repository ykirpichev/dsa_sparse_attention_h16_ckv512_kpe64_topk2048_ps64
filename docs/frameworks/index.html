The operation

For each of T tokens, 16 query heads, and up to 2,048 sparse key positions:

score = (q_nope · ckv + q_pe · kpe) · sm_scale
p     = softmax(score)          # computed in base 2
out   = p · ckv                 # the 512-d latent, not a separate value tensor
lse   = m + log2(l)             # base-2 log-sum-exp, −∞ when the row is empty

q_nope is [T, 16, 512] bf16, q_pe is [T, 16, 64], the caches are paged [pages, 64, dim], and sparse_indices is [T, 2048] int32 with −1 for padding. Padding may sit anywhere in the row. sm_scale is 0.1352337788608801. The kernels multiply by sm_scale · log2(e) once and stay in base 2 from there.

One plan, used by all four

A short token is scored by one program that walks the valid keys. A long token is split into G key-groups. Each group keeps a full 512-wide partial, because the program that merges column c has to read column c from every group. A group that only stored its own columns would have nothing to merge. G is 16 while T · 16 fits on the B200's 148 SMs, and smaller after that, so the programs that meet at the barrier are all resident.

Which path runs

A short token is scored by one program and never publishes a partial. A long token is split across key-groups. CUDA chooses from the token count: eight or more tokens take the per-token kernel. The other three choose from how many programs fit on the GPU at once. Triton also looks at where the last valid index sits. First place looks only at the token count: two tokens or fewer never split the keys, and three or more always do. PyTorch does not split at all. One host loop gathers the valid keys and runs one softmax over the row.

def reference(q_nope, q_pe, ckv_cache, kpe_cache, sparse_indices, sm_scale):
    """fp32 PyTorch form of the definition's reference loop."""
    n_tokens, n_heads, dim = q_nope.shape
    ckv = ckv_cache.reshape(-1, dim)
    kpe = kpe_cache.reshape(-1, kpe_cache.shape[-1])
    out = torch.zeros((n_tokens, n_heads, dim), dtype=torch.float32, device=q_nope.device)
    lse = torch.full((n_tokens, n_heads), float("-inf"), dtype=torch.float32, device=q_nope.device)
    for t in range(n_tokens):
        idx = sparse_indices[t]
        idx = idx[idx != -1].long()
        if idx.numel() == 0:
            continue
        kc = ckv[idx].float()
        kp = kpe[idx].float()
        score = (q_nope[t].float() @ kc.T + q_pe[t].float() @ kp.T) * float(sm_scale)
        lse[t] = torch.logsumexp(score, dim=-1) / math.log(2.0)
        out[t] = torch.softmax(score, dim=-1) @ kc
    return out, lse

Gather the sparse keys

Each program loads the keys named by its slice of the index row. CUDA issues 16-byte cp.async copies. Triton masked-loads inside the tile loop, which is where Triton pipelines. ThunderKittens stores uint4 into the swizzled shared tile. TileLang copies one element at a time: a 16-byte load comes back as a vector this frontend cannot index.

Score, softmax, and the output dot

The score is q_nope · ckv + q_pe · kpe, scaled into base 2, then an online softmax. The output dot reuses the keys that were just gathered. Invalid positions stay at −∞, so they add nothing.

Merge the partials

Each key-group keeps a full 512-wide partial. The program that owns a column range rescales every group's partial into one softmax and writes those columns. CUDA does this in a second kernel. Triton and ThunderKittens do it in the same launch, behind a counter. TileLang does it in a second kernel, and the host replays both from one CUDA graph.

Why the fused kernel is faster than first place

Doğaç Eldenk's kernel is the same idea: one Triton launch, 16 programs per token, and a counter that lets those programs merge. On the official 50-iteration run it averages 10.2 µs, 0.45× the CUDA submission. run_fused averages 8.6 µs, 0.37×, and it is faster on every one of the 23 workloads. The full five-way table is on the comparison page. The gap comes from when the keys are split, and from how long a tile is.

Where the code is

  • CUDA: solution/python/kernel.cu and mla_cta.cuh. The score reduction writes s_logits_tile[tid] = (g_idx >= 0) ? sum * sm_scale_log2e : −∞.
  • Triton: solution/triton/kernel.py, run_fused. One program per key-group. Below the threshold it writes its own columns and skips the barrier. Above it, every key-group stores the whole value.
  • TileLang: solution/tilelang/solution.py. T.gemm(q_s, k_s, score, transpose_B=True) is the score, and one T.gemm(p_s, k_s, mix) is the whole output. A second kernel merges. Both are captured in one CUDA graph.
  • Contest first place: Doğaç Eldenk's Triton kernel, shown in the First place tab. Two tokens or fewer use _small_t_kernel with a fixed block of 64. Three or more use _fused_split_combine_kernel with 16 splits and a block of 128.
  • PyTorch: reference in scripts/triton_profile_worker.py. The fp32 loop the other kernels are checked against. It is not timed with them.
  • ThunderKittens: solution/tk/attention.cu. mm_ABt scores 128 gathered keys by a 128-wide chunk of the latent. mm_AB mixes the softmax weights with the same latent. The loader is solution/tk/solution.py.

Why CUDA, ThunderKittens, and TileLang are slower

On the dense call (02d6ae9c, 8 tokens, 303 keys) Triton is one kernel and takes 11.0 µs. CUDA takes 51.8 µs in two kernels. ThunderKittens takes 104 µs in one kernel. TileLang's kernels take 46.2 µs and 6.6 µs, plus about 8 µs of small copies, so the GPU is busy for 60.8 µs. The span is 113 µs because the GPU waits between those launches.

CUDA was tuned for a 16-key WMMA tile and a second kernel that merges the partials. In the timed build, twelve of the 23 workloads took that per-head path, which is about 0.9 µs per tile. The source now picks the path from the token count: T >= 8 uses the per-token kernel, and a smaller call stays per-head. That shape rule was measured slightly faster than counting valid indices, and the decision is a comparison of T. The fused Triton kernel scores 32 to 128 keys in one pipelined tile and merges in the same launch. CUDA still wins the shortest call, 3.4 µs against 4.0. Past a handful of keys the 16-key tile and the second kernel are the whole gap: the dense call is 51.8 µs against 11.0.

ThunderKittens pays for the tensor-core tile. mm_ABt consumes 128 rows and a K that is a multiple of 64, and this problem has 16 heads and a 512-d latent, so most of each tile is padding. Scoring 128 keys is four K=128 steps plus the positional key. The output is eight more mm_ABs of 64 columns. Each step gathers into a swizzled tile, one thread issues the MMA, and every thread waits. One such tile is already about 50 µs on a token with two keys, which Triton scores in 4 µs. The 16-byte vector gather removed the scalar shared-memory cost. The number of MMA steps is still there.

TileLang pays for the gather and for two launches. A 16-byte load comes back as a vector this frontend cannot index, so a 128 by 512 key tile is copied one element at a time. The gemm itself is one call for the score and one call for all 512 output columns. The reported 95.9 µs geomean is that work plus the idle time between the partial kernel and the merge. Kernel-busy time is 39.6 µs.

Triton is one pipelined launch. The score, the softmax, and the output dot share the K that was just loaded, and the merge is a counter in that same kernel. On 16 heads by 512 that is worth more than the tensor-core instruction the other two are built around.

What is left to tune

ThunderKittens has a small-token opening and no dense one. A path that skips tcgen05 for a token under 128 keys would cut the calls that currently spend about 50 µs scoring a handful of keys. The dense call needs the 512-d multiply. Halving the number of steps means a K of 256, and doubling those tiles adds about 80 KB. The tiles already allocated, plus the running softmax, sit near the 227 KB a B200 block can hold, so that kernel was not built. The measured sequence is the one that fits: a scalar epilogue was 234 µs, half-width output MMAs were about 50 µs, and the wide score plus one mm_AB per 64 columns is the 47–104 µs in the table.

TileLang 0.1.15 has no unused knob that won a measurement. Block 128 beat block 64 (geomean 95.9 µs against 97.6). One output gemm beat eight chunk gemms. A CUDA graph of the two kernels beat folding them together with a grid sync, which moved the short call from 82 µs to 134 µs, and it beat the cython launcher, which took about 225 µs. A vectorized gather was slower than the element gather. The graph replays both kernels and still leaves the GPU idle between them. The remaining room is a later TileLang that can index a 16-byte load, or that can issue both kernels without that gap. It is not a parameter of this file.

What to ship

Ship run_fused. On the official 50-iteration run it averages 8.6 µs, 0.37× the CUDA submission, against 10.2 µs and 0.45× for the contest winner. It is faster than that kernel on every one of the 23 workloads, and faster than the CUDA submission on 22 of them. TileLang and ThunderKittens are correct, including scattered padding and token counts past the contest range, and they are the right way to read the algorithm in those languages. They are not the fast path for 16 heads and a 512-d latent.
