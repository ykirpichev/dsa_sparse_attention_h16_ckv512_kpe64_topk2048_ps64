The operation

For each of T tokens, 16 query heads, and up to 2,048 sparse key positions:

score = (q_nope · ckv + q_pe · kpe) · sm_scale
p     = softmax(score)          # computed in base 2
out   = p · ckv                 # the 512-d latent, not a separate value tensor
lse   = m + log2(l)             # base-2 log-sum-exp, −∞ when the row is empty

q_nope is [T, 16, 512] bf16, q_pe is [T, 16, 64], the caches are paged [pages, 64, dim], and sparse_indices is [T, 2048] int32 with −1 for padding. Padding may sit anywhere in the row. sm_scale is 0.1352337788608801. The kernels multiply by sm_scale · log2(e) once and stay in base 2 from there.

One plan, used by all four

A short token is scored by one program that walks the valid keys. A long token is split into G key-groups. Each group keeps a full 512-wide partial, because the program that merges column c has to read column c from every group. A group that only stored its own columns would have nothing to merge. G is 16 while T · 16 fits on the B200's 148 SMs, and smaller after that, so the programs that meet at the barrier are all resident.

Where the code is

  • CUDA: solution/python/kernel.cu and mla_cta.cuh. The score reduction writes s_logits_tile[tid] = (g_idx >= 0) ? sum * sm_scale_log2e : −∞.
  • Triton: solution/triton/kernel.py, run_fused. One program per key-group. Below the threshold it writes its own columns and skips the barrier. Above it, every key-group stores the whole value.
  • TileLang: solution/tilelang/solution.py. T.gemm(q_s, k_s, score, transpose_B=True) is the score, and one T.gemm(p_s, k_s, mix) is the whole output. A second kernel merges. Both are captured in one CUDA graph.
  • ThunderKittens: solution/tk/attention.cu. mm_ABt scores 128 gathered keys by a 128-wide chunk of the latent. mm_AB mixes the softmax weights with the same latent. The loader is solution/tk/solution.py.

What the gap is made of

On a dense 8-token call (02d6ae9c, 303 valid keys) Triton is one kernel and takes 11.0 µs. CUDA takes 51.8 µs across two kernels. ThunderKittens takes 104 µs in one kernel. TileLang's two kernels take 46.2 µs and 6.6 µs, and three small copies take another 8 µs, so the GPU is busy for 60.8 µs. The CUPTI span is 113 µs because the GPU sits idle between those launches while the host issues the next one.

ThunderKittens is paying for the shape of the tensor core. mm_ABt wants a 128-row tile and a K that is a multiple of 64, and this problem has 16 heads and a 512-d latent. Scoring 128 keys is four K=128 steps plus the 64-d positional key, and the output mix is eight more mm_ABs of 64 columns. Each of those is a gather into a swizzled shared tile, one thread issuing the MMA, and a parity wait. A single key tile is already ~50 µs on a nearly empty token, where Triton scores two keys in 4 µs. The same 16-byte vector gather the FP8 indexer uses is in this kernel. It removes the scalar shared-memory tax. It does not remove the number of MMA steps.

TileLang's partial kernel is the gather. One program loads a 128 by 512 bf16 tile one element at a time, because a 16-byte load comes back as a vector this frontend cannot index. That is the same constraint as the FP8 indexer port. The gemm itself is one call for the score and one call for all 512 output columns. Folding the merge into the same kernel with a grid sync was slower, not faster: the cooperative launch added host time and the span went from 82 µs to 134 µs on the shortest call. A cython launcher was slower still. The graph of the two kernels is the best launch this version of TileLang produced here.

Triton wins because the whole token is one pipelined launch. The score, the online softmax, and the output dot share the K that was just loaded, and the merge is a counter in that same kernel rather than a second launch. On this shape that is worth more than the tensor-core instruction either of the other two frameworks is built around.

What to ship

Ship run_fused. It is faster than the CUDA submission on 22 of the 23 workloads and faster than the contest winner on this suite. TileLang and ThunderKittens are correct, including scattered padding and token counts past the contest range, and they are the right way to read the algorithm in those languages. They are not the fast path for 16 heads and a 512-d latent.
