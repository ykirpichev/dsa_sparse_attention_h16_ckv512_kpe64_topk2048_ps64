DSA sparse attention on B200: CUDA vs Triton

MLSys 2026 FlashInfer contest kernel dsa_sparse_attention_h16_ckv512_kpe64_topk2048_ps64 · 23 contest workloads · NVIDIA B200 · Triton 3.7.0

Translating the CUDA submission to Triton line for line makes it 2.06× slower. Keeping the same Triton kernels and changing four settings makes it 1.81× faster than the CUDA submission (0.55× its latency). For scale, the kernel that won the contest track is also Triton and runs at 0.45× in the same run. Every version passes all 23 workloads.

Why the line-for-line port is slower

  1. The per-head kernel is 3–6× slower in Triton. It costs about 6.2 µs per 16-key tile against about 0.9 µs in CUDA. The CUDA kernel double-buffers its gather loads with cp.async; Triton only pipelines loads that feed tl.dot, and this kernel's dot products are element-wise sums, so num_stages has no effect on it.
  2. The dispatch thresholds are tuned for CUDA. Workloads averaging fewer than 210 valid keys per token go to the per-head kernel. That is 12 of the 23 workloads: CUDA's cheapest path and Triton's most expensive one.
  3. The per-token kernel is already faster in Triton. The 10 dense workloads that reach it take 42.3–43.5 µs in the port against 50.1–52.3 µs in CUDA.
  4. 16-key tiles are the wrong size for Triton. One loop iteration costs 4–5 µs almost regardless of how many keys it holds, so 64-key tiles with pipelined loads cut the cost per key several times over.
  5. Split-K is two Python launches. The GPU idles between the partial kernel and the merge kernel while Python prepares the second launch. The CUDA submission replays both from one CUDA graph.
  6. Small calls have a higher floor. The smallest call takes 5.3–6.9 µs in Triton against 3.6 µs in CUDA.

From the port to the tuned version

Each bar is one configuration of the same Triton file used for every workload, as geomean latency relative to the CUDA kernel. Left of the dashed line is faster than CUDA.

The tuned entry point, run_tuned, uses the per-token kernel for every workload with 64-key tiles and num_stages=3. One or two tokens run as a single kernel with no split. More tokens split the top-k axis 16 ways and replay the two launches from a CUDA graph.

How this was measured

  • One NVIDIA B200 on Modal, image flashinfer/flashinfer-ci-cu132, CUDA 13.2, torch 2.12.0.dev20260408+cu132, Triton 3.7.0. The contest evaluated Triton 3.6.0.
  • The headline numbers come from the official flashinfer-bench evaluator, all solutions in one container run. Latency is the span from the first kernel's start to the last kernel's end, so Python time before the first launch is not counted and time between launches is.
  • The CUDA kernel is the submission with its source split into readable headers; the algorithm and thresholds are unchanged.
  • Both the CUDA kernel and the faithful port cache their dispatch decision on the address of the index tensor. When a new workload's tensor reuses a freed address, the previous decision is applied. This sent workload 78b2e11c through the port's per-head kernel in the official run. The tuned entry point decides on shape only.
