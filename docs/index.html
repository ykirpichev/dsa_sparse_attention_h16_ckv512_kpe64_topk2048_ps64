DSA sparse attention on B200: CUDA vs Triton

MLSys 2026 FlashInfer contest kernel dsa_sparse_attention_h16_ckv512_kpe64_topk2048_ps64 · 23 contest workloads · NVIDIA B200 · Triton 3.7.0

Translating the CUDA submission to Triton line for line makes it 2.04× slower. Keeping the same Triton kernels and changing four settings makes it 1.86× faster than the CUDA submission (0.54× its latency). A new Triton kernel that splits and merges inside a single launch is 2.70× faster (0.37×). For scale, the kernel that won the contest track is also Triton and runs at 0.45× in the same run. Every version passes all 23 workloads. The same kernel in TileLang and ThunderKittens is timed on the same workloads in four frameworks, side by side, and that page sets the fused kernel next to the contest winner.

Why the line-for-line port is slower

  1. The per-head kernel is 3–6× slower in Triton. It costs about 6.2 µs per 16-key tile against about 0.9 µs in CUDA. The CUDA kernel double-buffers its gather loads with cp.async; Triton only pipelines loads that feed tl.dot, and this kernel's dot products are element-wise sums, so num_stages has no effect on it.
  2. The dispatch thresholds are tuned for CUDA. In this run, workloads averaging fewer than 210 valid keys per token go to the per-head kernel. That is 12 of the 23 workloads: CUDA's cheapest path and Triton's most expensive one. The CUDA source now uses the token count instead (T >= 8 takes the per-token kernel); that shape rule was measured slightly faster than the index count.
  3. The per-token kernel is already faster in Triton. The 10 dense workloads that reach it take 42.2–44.0 µs in the port against 50.1–52.0 µs in CUDA.
  4. 16-key tiles are the wrong size for Triton. One loop iteration costs 4–5 µs almost regardless of how many keys it holds, so 64-key tiles with pipelined loads cut the cost per key several times over.
  5. Split-K is two Python launches. The GPU idles between the partial kernel and the merge kernel while Python prepares the second launch. The CUDA submission replays both from one CUDA graph.
  6. Small calls have a higher floor. The smallest call takes 5.3–6.9 µs in Triton against 3.6 µs in CUDA.

From the port to the tuned version

Each bar is one configuration of the same Triton file used for every workload, as geomean latency relative to the CUDA kernel. Left of the dashed line is faster than CUDA.

The tuned entry point, run_tuned, uses the per-token kernel for every workload with 64-key tiles and num_stages=3. One or two tokens run as a single kernel with no split. More tokens split the top-k axis 16 ways and replay the two launches from a CUDA graph.

One launch: the fused kernel

run_fused is a different kernel, not a setting of the port. It launches once, with 16 programs per token. Every program first scans its token's index row for the last valid position, and all 16 then take the same path:

  • Short token (last valid position below 128): each program scores every key and accumulates 32 of the 512 output columns. Nothing is shared between programs.
  • Long token: each program takes every 16th key and publishes a partial softmax. A per-token atomic counter is the barrier. When all 16 partials are in, each program merges its 32 columns from them. This replaces the second launch of split-K, so there is no gap to hide and no CUDA graph to keep.

Three things account for the gain over the tuned version:

  1. The path is chosen per token, not per call. Workload 68d6817d has 6 tokens with at most 32 keys each. The tuned version and the first-place kernel both split it because of its token count and take 11.1 µs and 11.2 µs. The fused kernel takes 4.4 µs.
  2. The tile is sized to the work. A tile costs about as much as its size whether its slots hold keys or padding: the smallest call takes 4.2 µs with a 32-slot tile, 5.1 µs with 64 slots and 6.0 µs with 128. Both paths therefore pick the smallest of the three that covers the token. The 2 two-token workloads whose longer token has 288–337 keys went from 10.5 µs to 8.0–8.1 µs this way (19.2–23.0 µs in CUDA, 14.3–16.4 µs for first place).
  3. Every tile is written as a loop, even a single one. Triton pipelines loads only inside a loop. The same 64-slot tile as straight-line code took 7.2 µs instead of 5.2 µs.

On a dense workload the fused kernel takes about 11 µs. Runs with parts of the kernel switched off put roughly 3 µs in the launch, the query load and the row scan, 4 µs in the 128-key tile, 2 µs in publishing and merging the partials, and 1.5 µs in the barrier. These are estimates from differences between runs.

Limits:

  • The barrier only opens if every program of the launch is on the GPU at the same time. The kernel therefore uses 16 programs per token up to 9 tokens and 8 up to 18 (a B200 has 148 SMs), and run_fused hands larger calls to run_tuned. The first-place kernel uses the same kind of barrier with 16 programs per token at any token count. On a synthetic 12-token call (192 programs) it did not return before the run's time limit, which is consistent with this constraint. The contest workloads stop at 8 tokens.
  • The partials live in one workspace per call shape, so concurrent calls from several streams would collide. The port's split-K workspace has the same property.
  • The benchmark repeats one input, which would hide a merge that read partials left over from the previous call. A separate check runs 180 synthetic calls with new contents each time, 1 to 20 tokens, padding at the tail or scattered through the row: the largest output error is 0.0067 and the largest lse error is 7.6e-06.

How this was measured

  • One NVIDIA B200 on Modal, image flashinfer/flashinfer-ci-cu132, CUDA 13.2, torch 2.12.0.dev20260408+cu132, Triton 3.7.0. The contest evaluated Triton 3.6.0.
  • The headline numbers come from the official flashinfer-bench evaluator, all solutions in one container run. Latency is the span from the first kernel's start to the last kernel's end, so Python time before the first launch is not counted and time between launches is.
  • The CUDA kernel is the submission with its source split into readable headers; the algorithm and thresholds are unchanged.
  • Both the CUDA kernel and the faithful port cache their dispatch decision on the address of the index tensor. When a new workload's tensor reuses a freed address, the previous decision is applied. This sent workload 78b2e11c through the port's per-head kernel in the official run. The tuned entry point decides on shape only, and the fused kernel decides inside the kernel from the index row itself.
